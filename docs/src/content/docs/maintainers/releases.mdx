# Releases & Versioning

KoAkademy deliberately separates rolling delivery from stable releases:

| Source event                  | GitHub Release                   | GHCR and Docker Hub tags                                           |
| ----------------------------- | -------------------------------- | ------------------------------------------------------------------ |
| Pull request                  | None                             | Build validation only; nothing is pushed                           |
| Merged `master` commit        | None                             | Immutable `sha-<40-character-commit>` and mutable `edge`           |
| Merged Release Please PR      | Draft until publication succeeds | `sha-<commit>`, `edge`, `vX.Y.Z`, `X.Y.Z`, `X.Y`, `X`, and `latest` |

Both registries receive the same `linux/amd64` and `linux/arm64` manifest:

- `ghcr.io/yukazakiri/koakademy`
- `yukazaki/koakademy`

Use an exact `vX.Y.Z` image in production. `latest` is a convenience alias for the newest verified stable release. `edge` is unsupported rolling software and may change after every successfully delivered `master` commit. The historical `dev-latest` and `v*-dev.*` tags and prereleases remain available but are frozen.

## Pull requests and version selection

Pull request titles use Conventional Commits because squash merging makes that title the commit Release Please evaluates. A metadata-only workflow automatically normalizes a plain-language title from its topic, description, labels, and changed-file names; maintainers must review the inferred type, scope, and breaking marker before merge:

| PR title prefix                                   | Proposed SemVer change                                                                   |
| ------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| `fix:`                                            | Patch                                                                                    |
| `feat:`                                           | Minor                                                                                    |
| `feat!:`, `fix!:`, or a `BREAKING CHANGE:` footer | Major                                                                                    |
| `docs:`, `chore:`, `ci:`, `test:`, and similar    | Changelog entry without an automatic version bump unless paired with a releasable change |

Examples:

```text
fix(installer): preserve an existing Swarm
feat(enrollments): add fee overrides
feat(api)!: replace the student verification response
chore(release): release 1.12.0
```

The repository uses squash merge only, linear history, and the stable `CI / required` check. Release Please is initialized from `v1.11.0`; later historical `-dev` tags are not release boundaries. The first generated release PR is expected to propose `1.12.0` from the feature commits after that stable boundary, and remains subject to maintainer review.

An exact Release Please metadata-only pull request takes the fast CI path: it validates the manifest version, tracked version, title, changelog entry, and allowed three-file change set without rerunning the application suite. Any unexpected file falls back to full CI.

## Trusted delivery

`delivery.yml` is triggered directly by a push to `master`, but its privileged path runs only when all of these are true:

- the event is `push`;
- the ref is exactly `refs/heads/master`;
- the event repository exactly matches this repository;
- the immutable event `after` SHA matches the workflow SHA.

No checkout or secret access occurs before that trust decision. Pull-request CI is not repeated after merge, and administrators remain able to use the repository's existing branch-protection bypass. On ordinary commits, Release Please creates or updates one reviewed release PR. Delivery performs the only multi-architecture build for every `master` commit, verifies it, and moves `edge` only if that commit is still the current branch head.

When the release PR is merged, Release Please:

1. updates `CHANGELOG.md`, `.release-please-manifest.json`, and only the `version` field in tracked `version.json`;
2. force-creates the strict `vX.Y.Z` tag;
3. creates a draft GitHub Release.

Delivery then generates runtime build metadata without committing it, builds and pushes immutable SHA tags to both registries, verifies identical digests and both architectures, generates BuildKit SBOM/provenance records plus GitHub provenance attestations, and only then promotes release aliases. Every automatic delivery promotes the same verified image to `edge`; a stable release commit therefore updates both `edge` and its stable aliases without a duplicate build. Exact SemVer aliases are immutable. Major, minor, and `latest` aliases move only when the recovered or newly released version is the newest applicable stable tag.

The draft is published and marked latest only after container verification, alias promotion, release asset upload, and checksums all succeed. Immutable SHA references remain the audit and rollback source of truth.

## Version metadata

The tracked `version.json` records the latest stable source version. Release Please changes only its `version` field. During delivery, `scripts/generate-version-metadata.sh` creates the image-specific file in the runner, including:

- stable version or edge SemVer build identity;
- immutable image reference;
- full commit;
- UTC build timestamp;
- Actions run URL;
- `stable` or `edge` channel.

That generated file is copied into the image but never committed back to `master`. A stable copy is also attached to the GitHub Release. This prevents delivery reruns from creating bot metadata commits.

## Stable release assets

Every stable GitHub Release contains:

- `version.json`
- `compose.production.yaml`
- `.env.production.example`
- `install.sh`
- `install.ps1`
- `SHA256SUMS`

Verify an asset after download with:

```sh
sha256sum --check SHA256SUMS
```

## Required configuration

| Setting                | Location and purpose                                                                                                                                                                      |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `RELEASE_PLEASE_TOKEN` | `release-automation` environment secret containing a dedicated fine-grained repository token with Contents, Pull requests, and Issues read/write; do not reuse `PROJECT_AUTOMATION_TOKEN` |
| `DOCKERHUB_IMAGE`      | Repository variable, currently `yukazaki/koakademy`                                                                                                                                       |
| `DOCKERHUB_USERNAME`   | Repository or `container-publishing` environment secret                                                                                                                                   |
| `DOCKERHUB_TOKEN`      | Repository or `container-publishing` environment secret                                                                                                                                   |
| `release-automation`   | GitHub environment used by the Release Please job                                                                                                                                         |
| `container-publishing` | GitHub environment used by registry publication                                                                                                                                           |

Docker Hub is mandatory, not an optional mirror. The built-in GitHub token publishes GHCR packages and GitHub attestations. `RELEASE_PLEASE_TOKEN` must be fine-grained and restricted to this repository.
Both privileged environments accept deployments from protected branches only, so a manual run cannot select an unreviewed workflow ref.

Create `RELEASE_PLEASE_TOKEN` from **GitHub profile → Settings → Developer settings → Personal access tokens → Fine-grained tokens → Generate new token**:

1. Set the resource owner to `yukazakiri` and select only `koakademy`.
2. Set repository permissions **Contents**, **Pull requests**, and **Issues** to **Read and write**. Leave every other permission at its default.
3. Choose a finite expiration and generate the token. Copy it immediately; GitHub does not show it again.
4. Open **koakademy → Settings → Environments → release-automation → Environment secrets**, create `RELEASE_PLEASE_TOKEN`, and paste the token value.

Never paste the token into a workflow, issue, pull request, command history, or repository file. Rotate it before expiration and rerun the failed Delivery job after replacement.

## Recovery dispatch

Use **Actions → Delivery → Run workflow** only to recover an existing strict `vX.Y.Z` tag. The workflow rejects prerelease, missing, malformed, or invented tags and never creates or moves a Git tag. It may rebuild a missing immutable SHA image, recreate a missing draft for the existing tag, re-upload assets, and finalize publication.

Recovery of an older stable version never rolls back `latest`, a major alias, or a minor alias past a newer matching stable version. If an immutable SemVer tag already points to another digest, recovery fails instead of moving it.

## Verification and rollback

Before announcing a release, check both registries anonymously:

```sh
docker buildx imagetools inspect ghcr.io/yukazakiri/koakademy:vX.Y.Z
docker buildx imagetools inspect yukazaki/koakademy:vX.Y.Z
```

Confirm `linux/amd64` and `linux/arm64` are present and the top-level digests match. Smoke-test the production Compose contract and `/up`, then exercise login, queues, uploads, and one PDF render.

Rollback by selecting the previous reviewed exact `vX.Y.Z` tag, never by guessing the former value of `latest` or `edge`. Read that release's migration notes first; if the earlier application cannot read the migrated schema, restore the matching database backup and image together.
