## One source owner per extension

`Modules/` is a Laravel module layout and PHP namespace. `extensions/starter/`
is the development template. Neither name determines whether a feature is free,
paid, or installed. Production extension code is delivered through Composer into
`vendor/`, compiled into the application image, and managed in Extensions & licenses.

The established domain extensions have these source owners:

| Extension             | Composer package                    | Source repository                                                                         |

to another feature's repository. The starter remains development-only.

## Complete the 1.1 package handoff

The six merged package changes reconcile their source with core commit
`ff3cae913b14b11737380446472f2119e3e60b28`. This includes Library stock accounting,
authorization, and school isolation fixes, the missing Inventory migration,
Announcement schema-cache invalidation, Cashier behavior, and current medical
and notification fixes. Provider paths are relative to the package rather than
dependent on discovery order.

1. Merge the package publication metadata changes, then tag `v1.1.0` from each reviewed package commit, whose `module.json` version is exactly `1.1.0`. Do not replace existing tags.
2. Submit each public repository to Packagist using a maintainer account for the `koakademy` vendor namespace. Verify the package, version, and source commit are visible.
3. Review and sign the Marketplace registry's generated catalog PR using the existing key.
4. Replace the application's temporary branch aliases with stable `^1.1` requirements, remove the six temporary Git fallbacks, update their lockfile entries, and run the full checks. Build and deploy the new image through the normal release process.

The application currently locks merged `master` commits with inline aliases.
Packagist is preferred for public packages; direct Git fallbacks keep the six
packages installable until their first compatible releases appear there.
The signed Marketplace catalog and legacy Composer index remain separate from
Packagist publication.

## Preserve existing installations

Remove a bundled directory in the same application dependency change that adds
its Composer package. The host rejects duplicate module names, aliases, and
package identities. Moving the directory to `extensions/` would preserve the
duplicate ownership problem.

Keep existing PHP namespaces, provider names, routes, table names, historical
migration filenames, and module identities. Existing imports and database rows
then continue to refer to the same feature. Do not reset the school database,
delete module-installation records, run `migrate:fresh`, or reseed customer data.

In the release container, run the normal migrations, synchronize permissions,
validate installed contracts, clear/rebuild application and module caches, and
roll all workers. Keep `MODULE_SCAN_VENDOR=true`. Synchronize installation
metadata without overwriting administrator enable/disable choices. Preserve
the existing persistent module status file and acknowledge a completed rollout
only after all replicas are healthy.

The application requires all six packages by default to preserve the features
already delivered by its images. Administrators can keep any of them disabled.
Community extensions do not acquire a commercial license requirement through
this ownership migration. Enterprise capabilities still use their separate
school entitlement and user-permission checks.

## Future contributions

Change an extension in its own repository, run its package and host checks,
release a new tag, publish it to Packagist, review/sign the catalog, then update the host lockfile and
image. Change shared SDK contracts or cross-extension integration in core.
Additional frontend dependencies require a host npm lockfile change. Package
CI installs the contribution into a clean host checkout, removes its bundled
duplicate where needed, and builds both browser and SSR assets.

The host's Tailwind sources explicitly include installed packages' frontend and
view directories, and the Filament theme includes their resource classes and
views. Keep those package layouts when contributing UI so moving code into
Composer's ignored `vendor/` directory does not remove its generated styles.
