# Admin Portal

Administrative staff work in two connected areas: the **administration panel** at `/admin` (records, resources, and settings) and the **admin workspace** (guided operational screens such as enrollment processing and finance). What you see depends on your role and permissions.

## Sign-in and security

- Sign in with your staff account. Administrators can require **two-factor authentication** (authenticator app or e-mail code) and **passkeys**.
- Use the **school-year and semester selector** in the panel header before entering data, so records land in the correct academic period.
- Press **Ctrl+L** (Windows/Linux) or **⌘L** (macOS) for global search across students, classes, and other records.

## Dashboard

The panel dashboard summarizes operations with widgets: enrollment, retention, and attrition statistics, demographics, scholarship distribution, clearance status, geographic distribution, recent enrollments and students, resource availability, and upcoming events. Widgets respect the selected academic period and your permissions.

## Records and resources

The sidebar groups the core resources:

| Resource | Typical work |
| -------- | ------------ |
| Students | Student profiles, documents, signature capture, enrollment checklists, clearances |
| Student Enrollments | Enrollment records, statuses, and history |
| Faculties and Accounts | Teaching staff and user accounts |
| Courses and Departments | Programs, curriculum structure, and departments |
| Classes and Rooms | Sections, schedules, capacity, and room assignment |
| Events | School calendar events shown on dashboards |
| Schools | Institutions in a multi-school deployment |
| Users and Roles | Accounts, role assignment, and permission review |
| Senior High School | SHS strands and SHS student records (cluster) |

Additional panel pages cover **Timetable** management, **Student Clearances**, **Backups**, and **General Settings**.

## Enrollment processing

The admin workspace provides the operational enrollment flow:

1. **Search and review applicants.** Look up a student and open their application.
2. **Verify academically.** The registrar or department head verifies subjects, documents, and assessment.
3. **Verify payment.** The cashier confirms or records payment.
4. **Complete or reopen.** Finish the enrollment, or use the authorized undo/reopen action with a reason.

Enrollment reports, analytics, and assessment PDFs are available from the same area. Configuration of availability, eligibility, tuition, and approvals is handled by **Enrollment Blueprints** — see the Blueprint guides in the navigation.

## Finance

The finance area provides dashboards, payment recording, invoices and receipts, and reports. Statements of account can be issued to students and include a signed public verification link. Bulk assessment PDFs are generated in the background; downloads appear when ready.

## System management

The System Management area centralizes institution configuration: school profile and branding, academic periods, grading rules, student identifier formats, deployment mail status, notification templates, analytics, SEO, social sign-in providers, API keys, and the **Feature Toggles** page that switches portal features on or off. SMTP and provider credentials are configured on the server through `koakademy configure mail`, not in the web application.

### Analytics providers

**System Management → Analytics** controls every third-party analytics script the portal loads. A fresh install sends none.

You can add as many providers as you need, including several instances of the same provider (for example one Umami site per domain). Each instance is saved as its own entry with its own enable switch, so you can turn one off without touching the others. A master switch above the list disables all of them at once.

Add a provider with the picker at the top of the page. Its form is generated from the provider's own definition, so the fields shown always match what that service needs. The available providers are:

| Provider | Hosting | Notable options |
| -------- | ------- | --------------- |
| Umami | Self-hosted | Click and scroll heatmaps, session replay (needs v3.2+) |
| Plausible | Self-hosted or cloud | Site domain, API host |
| Matomo | Self-hosted | Site ID; heatmaps and recording are paid plugins |
| PostHog | Self-hosted or cloud | Autocapture for click maps, rage-click detection |
| Fathom | Cloud or Fathom Lite | Lite (self-hosted) or Cloud |
| OpenPanel | Self-hosted | Session replay, outgoing-link tracking |
| GoatCounter | Self-hosted | No cookies, no unique visitor IDs |
| Countly | Self-hosted | Consent requirement toggle |
| Counter.dev | Cloud | Cookieless, no signup |
| Cloudflare Web Analytics | Cloud | Beacon token from your Cloudflare zone |
| Simple Analytics | Cloud | Cookie-free |
| Google Analytics 4 | Cloud | GA4 measurement ID |
| Microsoft Clarity | Cloud | Session recordings and click heatmaps |
| StatCounter | Cloud | Project and security code |
| Yandex Metrica | Cloud | Click map toggle |
| Custom Snippet | Any | Paste any HTML or script; add as many as you like |

Every entry can be given a name, so two instances of the same provider stay distinguishable, and a **custom snippet override** field lets you replace the generated markup when a service needs something the generator cannot express.

:::caution[Student data]
Providers marked *Hosted* send visitor data to a third party, which makes them a data processor for your institution. You have a `StudentMedicalRecords` module and minors' records in scope, so review your obligations under the Data Privacy Act and your guardian-consent position before enabling Google Analytics, Clarity, or Yandex Metrica. Prefer the self-hosted options.

Session replay (Umami, OpenPanel, Clarity, Yandex) records what appears on screen, including student names, grades, and medical details. If you enable it, use the strictest masking your provider offers and set a low sample rate.
:::

:::tip[Which one for click and heatmap data?]
Since Umami v3.2, self-hosted Umami gives you click and scroll heatmaps with no third-party processor involved. PostHog's autocapture is the stronger choice if you want dead-click and rage-click detection as queryable data rather than a visual overlay.
:::

:::tip[Audit trail]
Administrative changes are recorded under **Audit Logs**. When something looks wrong, check there first before changing a record back.
:::
